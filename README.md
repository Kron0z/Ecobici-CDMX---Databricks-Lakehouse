# Project: Ecobici CDMX — Databricks Lakehouse

## Objective

Portfolio project simulating the work of a Data Engineer in a real company, using public mobility data from Mexico City (Ecobici bike-share system). The goal is twofold:

1. Build a complete Lakehouse pipeline (Bronze → Silver → Gold) on Databricks.
2. Serve as hands-on preparation for the **Databricks Data Engineer Associate** certification, specifically covering: Unity Catalog (governance and permissions), external vs. managed tables, incremental ingestion, Lakeflow Jobs, and monitoring with System Tables.

## Data Sources

- **Ecobici GBFS API** (`https://gbfs.mex.lyftbikes.com/gbfs/gbfs.json`): real-time station status (periodic snapshots via a Python script).
- **Historical trip CSVs**: open data published by Mexico City, downloaded manually and stored in a Volume.

## Architecture

Medallion architecture built on Unity Catalog:

```
cdmx_project (catalog)
├── bronze   (raw, untransformed data)
├── silver   (cleaned and validated data)
└── gold     (aggregated data, ready for analytics/dashboards)
```

Raw files (downloaded CSVs and JSON API snapshots) are first stored in a **Volume** (`cdmx_project.bronze.raw_data`) before being converted into Delta tables.

## Technical Decisions

### Governance and Permissions (Unity Catalog)

A role-based permission scheme was set up:
- **Engineer** role (me): full control over `bronze` and `silver`.
- **Analyst** role (test user): read-only access (`SELECT`) to `gold` only.

```sql
GRANT USE CATALOG ON CATALOG cdmx_project TO `analista_demo`;
GRANT USE SCHEMA ON SCHEMA cdmx_project.gold TO `analista_demo`;
GRANT SELECT ON SCHEMA cdmx_project.gold TO `analista_demo`;
```

### External vs. Managed Tables

Both table types were used deliberately to understand the difference in data lifecycle:

| Table | Type | Why |
|---|---|---|
| `bronze.trips_history` | **External** (explicit `LOCATION`) | The data already existed as files in the Volume; Databricks only references the location, it doesn't own it. |
| `bronze.station_status` | **Managed** (no `LOCATION`) | Data generated by the pipeline itself (API snapshots); it makes sense for Databricks to own its full lifecycle. |

**Test performed:** running `DROP TABLE` on the managed table deleted the underlying Delta files. Running `DROP TABLE` on the external table only removed the metadata — the Delta files in the Volume remained intact.

```sql
-- External table (files survive DROP TABLE)
CREATE TABLE IF NOT EXISTS cdmx_project.bronze.trips_history
USING DELTA
LOCATION '/Volumes/cdmx_project/bronze/external_tables/trips_history/'
AS SELECT * FROM read_files(
  '/Volumes/cdmx_project/bronze/raw_data/trips/',
  format => 'csv',
  header => true,
  inferSchema => true
)
```

```python
# Managed table (files are deleted along with the table)
df = spark.sql("""
    SELECT * FROM read_files(
        '/Volumes/cdmx_project/bronze/raw_data/*station_status.json',
        format => 'json'
    )
""")
df.write.format("delta").mode("append").saveAsTable("cdmx_project.bronze.station_status")
```

### API Snapshot Ingestion

A Python script downloads the GBFS feed with a timestamp in the file name, allowing historical snapshots to accumulate and, later, enabling incremental ingestion (Auto Loader) over new files.
